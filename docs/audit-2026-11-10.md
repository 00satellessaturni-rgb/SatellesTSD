# SatellesTSD — third audit, after the first audit's revisit and the second window's features (2026-11-10, version 0.28.0, commit e10caab)

**How it was made.** Eight Opus finders over the work since the second audit closed (the diff from 12da692 to e10caab: 39 commits, plan items 22–54, decisions 124–163): six on the changed areas (the row split; the period's files and the conflict tab; matching and import; the declaring; the register lookups; the store, the window and the update), one regression sweep of the whole monthly flow for interactions between the new features, and one for overlooked items (the plan's words against the code and the tests, the README, the texts, rules that drifted apart). The second window's features (several files out at once, the conflict tab, the row split) were looked at hardest. An Opus refuter tried to disprove every finding against the code and the plan's decisions; what survived is listed below with the refuter's corrected claim and severity. 20 findings were raised, 5 refuted, 15 confirmed: 1 critical, 3 major, 10 minor, 1 nit. The critical and the three majors (items 1, 2, 5, 9) were fixed the next day on the owner's word, item 55 of the plan's owner's list, and released as 0.29.0; the minors and the nit (items 4, 6–8, 10–15) the same day, item 56 — and item 3 was left as it is by decision 172. Every heading is closed.

Severity: critical = wrong tax or declaration data, or data loss; major = a flow the accountant needs that breaks or misleads; minor = a wrong message or an edge case with a workaround; nit = cosmetic.

## The short list — distinct issues that matter

1. **A re-read can move a row's decisions onto another row** (item 2, critical). "Loe uuesti" finds each decided row again by its fingerprint, but every row without a payee (a fee, a card payment) has an empty fingerprint and is told apart only by its position. A re-read that changes which rows have a payee shifts those positions: a category, a note or the parts of a split land on a different row, and the log says they were carried. A part can then be declared from a row it never belonged to.
2. **A part split off a row can pick up a category by itself** (item 1, major). A part is meant to have no category until the accountant gives it one. When the row had no category from the search (the rows on the conflict tab, the ones the split was made for), the part is stored as "follow the search", so a later search that does find a category makes the part a salary and it is declared by default.
3. **Facts checked for one day are not flagged when the person's day changes within the month** (item 5, major). The check that warns about facts of another month does not see a control date that moved inside the same month, after the review changed which payments are the person's.
4. **An update restarts on the command line's store, not the one in hand** (item 9, major). After a store is chosen in the window of a program started with `--store`, an update starts the new version with the old `--store`, which opens and upgrades that other store.
5. The minors (items 3, 4, 6–8, 10–14) and the nit (15): a name-search over-match that drops the right person's row; old card-export sheets refused as money in with no hint to re-read; three gaps in how the control date and the lookup's lines treat edge cases; a dirty card left over another company's view on Cancel; an update window opening over an open dialog; totals drafts left after every file is taken out; two README gaps; one misleading refusal text.

## The row split

### 1. [major] A part split off a row the run gave no category to follows a later run's category and is then declared by default — FIXED (item 55 of the owner's list, 2026-11-11)

bug — `SatellesTSD.Core/Review/ReviewWorkspace.cs:571`

Confirmed from the code. SetAmount (SatellesTSD.Core/Review/ReviewWorkspace.cs:571) stores a new part as ReviewLine.PartOf(..., noCategory: payment.DefaultCategory is not null). The run gives a default category only for a Matched verdict (line 702), so on an Ambiguous row (the rows on the conflict tab) or a row with no category, the part is saved with Category = null and NoCategory = false. That means "follow the run", not "none". Parts are carried across runs: partsByRow at line 96 feeds Emit at lines 248-256, which goes through FromHit. In FromHit, line 703 computes category = overlay is {NoCategory:true} ? null : overlay?.Category ?? defaultCategory. So once the masks are changed and "Otsi maksed" runs again with a Matched verdict (say a salary category), the part gets that category. It then gets a type from TypeCodeFor (line 705) and DefaultDeclare = true (line 713) when the person, the month and the amount are in order. The next "Koosta read" declares it. This goes against decision 150, which says a part gets no category, "(puudub)", "so no type and not declared until the accountant gives it one". The same drift happens in SetCategory (line 464): on a part whose run had no category, "(puudub)" stores NoCategory = false. Two things temper the severity. It needs a mask change followed by a new search. And after that search the grid does show the part's new category, so the accountant has a chance to see it. The amount would still reach the declaration as salary without any warning, so major (a misleading flow) rather than critical.

**Fix:** In SetAmount, save a new part with PartOf(..., noCategory: true) whatever the run's verdict was. In SetCategory, when the payment is a part and the accountant picks none, store NoCategory = true, i.e. NoCategory = payment.IsPart || payment.DefaultCategory is not null. If the accountant names a category on a part, store it explicitly instead of collapsing it to null when it equals the run's category. Then a part never takes on a later run's verdict. IsPayeeRow and the lookups already treat NoCategory as none, so nothing else has to change.

## The period's files and the conflict tab

### 2. [critical] "Loe uuesti" matches payee-less rows by position, because they all have an empty fingerprint, so a re-read can move a row's decisions and split parts onto a different row and still report them as carried — FIXED (item 55 of the owner's list, 2026-11-11)

bug — `SatellesTSD.Infrastructure/SqliteStore.Imports.cs:197`

The finding is real. ReplaceImport (SqliteStore.Imports.cs:155-184) carries each review_line by RowKeys (197-212), keyed on (sheet index, RowHash, ordinal of that RowHash within the sheet). StatementParser gives a real fingerprint only to rows with a counterparty (StatementParser.cs:423, HashOf). Blank rows (314), repeated header rows (321) and payee-less rows (387, built from Skipped at 434-435) all keep RowHash "". So on a sheet, every payee-less row is told apart only by its place among all the blank, header and payee-less rows. That is a position, not the content fingerprint decision 131 asks for ("the n-th row of a fingerprint").

Payee-less rows are listed and take decisions (ReviewWorkspace.cs:169; plan S14: the store admits a decision and a declared line on them, including a person named by hand). Splits are review lines on the row and are carried the same way (decision 150).

How it goes wrong: a re-read can change which rows are named (a changed layout's name column, a different header row) or add or remove a blank or header row ahead of a decided payee-less row. Every later empty-hash ordinal then shifts, newRows.TryGetValue (174) finds the wrong row, and the line counts as carried (177). RereadDone then reports the decisions as carried and nothing says they moved. Nothing checks a part against the new row's amount. The row's own share is whole minus parts (ReviewWorkspace.cs:250-251), so it can go negative (-145 in the scenario).

Results: the accountant's decisions on the original row are lost from it in the store. A person + category + Deklareerimine decision moved onto another fee row declares that row's amount for the person after the next search and build, with no further step by the accountant. A moved part declares its amount from the wrong row once it gets a category.

This is not closed by an earlier refutation. The item-23 review refuted "the fingerprint-only carry is the design", but this defect is that payee-less rows have no fingerprint at all. Named rows are not affected.

**Fix:** In RowKeys, key a row whose stored RowHash is empty on a fingerprint computed from its stored fields: StatementParser.HashOf over account, date or date text, amount or amount text, direction and description, plus the skip reason. This also covers stores that already hold empty hashes. Leave Blank and Header rows out of the keys, so they never shift an ordinal. Optionally also give NoName rows that hash in StatementParser.cs:387. As a guard, carry a line holding an amount (a part) only when the old and new rows' amounts are equal; otherwise drop it and count it as dropped.

## Matching and import

### 3. [minor] The uniqueness check reads a masked word of a multi-word mask as a pattern, so an unrelated surname that merely begins with the masked letters counts as a competitor and drops the right person's row — LEFT BY DECISION (decision 172, the owner's word 2026-11-11)

bug — `SatellesTSD.Core/Matching/NameSearch.cs:134`

The finding holds. Take a register person whose surname has two words, and a bank cell that spells the second word one letter differently. The exact level misses, and so do the glued mask and the first spaced masks; the first mask that hits is the one whose last word ends in a star, for example "AL*" (SpanOf, NameSearch.cs:95-120, Search :184-202), with the first name beside it. That hit used a mask, so the uniqueness check runs (:236-253). It calls CouldMean for each competitor, meaning another register person with a different personal code (:27, :182). For a person with the same first name and an unrelated one-word surname that merely begins with "AL", the substring test at :134 fails, but the word branch at :134 then tests each mask word as a Like pattern against the other person's whole surname, and "AL*" matches it. The first name matches at :135, so CouldMean returns true. The row goes into Dropped with that other person named as the conflict (:243-251), and the right person gets no hit at that level. The other person's own search never finds this cell, because no token is Like their surname. Decision 143 limits the extra rule to "a person whose name is one of its words, whole", and says "a surname merely holding a word of the mask is no competitor". A masked word like "AL*" is not a whole word, so the code is broader than the decision. The same over-match happens in the first-name word branch at :135 for a double first name. The result is a salary left unmatched, with a misleading conflict name. The accountant can still assign the row by hand, so this is minor.

**Fix:** In CouldMean's word branches (:134 and :135), count a competitor only when one of the mask's words without '*' or '?' equals their name (the case decision 143 describes). If a masked word should still yield a competitor, it must be one whose name is Like the cell token that word covered, not anyone Like the mask word. That needs CouldMean to receive the covered tokens from SpanOf's span in Search.

### 4. [minor] Card-export (source1) sheets stored before 0.16.0 keep their all-Credit reading; since decision 141 their payouts are refused as MONEY_IN with no hint to re-read them — FIXED (item 56 of the owner's list, 2026-11-11)

gap — `SatellesTSD.Core/Review/ReviewChecks.cs:52`

This is real, and the harm is narrow. Before 32f93b0 the source1 layout read the always-positive "Orig amount" under DirectionRule.Sign. StatementParser.cs:373 maps a positive amount to Credit, so every row of such a file got Direction.Credit. The direction is stored per row (SqliteStore.Imports.cs:235 writes it, :498 reads it back) and is not derived again, so those rows stay Credit until the file is read again, which is what the commit says ("keep their old reading"). After 722421d (decision 141) every reader of the direction treats them as money in: FromHit sets moneyIn and turns the default declare off (ReviewWorkspace.cs:712-713), ReviewChecks.Of refuses a tick with MONEY_IN (ReviewChecks.cs:52-54), the salary sums skip them (ReviewWorkspace.cs:809), Deklareerimata skips them (ReviewView.cs:160), they count as the accountant's choice (ReviewWorkspace.cs:878), and PayeePersons skips them (PayeePersons.cs:42). Concrete case: a Draft month holds a source1 file imported under 0.11.0-0.15.0. The accountant had put a salary category on a payout by hand, because the categorizer's side check (Categorizer.cs:111) gave a D/C error. The salary is now left out without a word. Ticking it gives MONEY_IN, whose text calls the row money in and points at a refund correction in e-MTA. Nothing marks the sheet as read by an older layout. The only use of the stored layout snapshot is the DirectionIsAssumed test at ReviewWorkspace.cs:153. Why minor and not more: decision 141's behaviour for genuine Credit rows is intended. The grid's D/C column shows "C" on these rows, which is a visible clue. "Loe uuesti" (decision 131) fixes it fully: it reads with the current layout, keeps the decisions by fingerprint and rebuilds the drafts. The stores affected are only those with source1 files imported in the roughly one-day window between 0.11.0 (2026-11-04) and 0.16.0 (2026-11-05), and only while their months are Draft. One more point for the fix: such old readings also carry "Orig amount"/"Orig currency", which is the card payment's own currency. For those rows reversing the direction alone would be wrong, and only a re-read is sound.

**Fix:** When the review is built, flag every source1 sheet whose stored layout snapshot (ImportSheet.Layout) reads Roles.Amount == "Orig amount", or more generally whose snapshot differs from the layout now in force for the same id. Show a note in the review or the files dialog that names the file and suggests "Loe uuesti". Do not change the stored direction in place: the stored amounts and currencies are the old ones too.

## The register lookups

### 5. [major] Facts checked for one day are not flagged when the review later dates the person to another day of the same month — FIXED (item 55 of the owner's list, 2026-11-11)

gap — `SatellesTSD.Core/Declare/PeriodDeclarer.cs:482`

Confirmed from the code. Since decision 138, each person's facts are checked for their latest payout in the review. LookupRunner.LookUpAsync works the answer out for that day: residency through IsResidentOn(controlDate) at LookupRunner.cs:291, membership and rate through ApplyPension's MemberOn and RateOn(controlDate) at LookupRunner.cs:362-363. It then stamps the person with FactsControlDate = controlDate (LookupRunner.cs:304 and :394). The build's only staleness check (PeriodDeclarer.cs:482-494, FACTS_OF_ANOTHER_MONTH) compares that stamp with the month only. Nothing compares it with the day the review gives the person now: LookupRunner.ControlDateFor is called only from PeriodPipeline.cs:449 and :460, for the card's own check.

Two ways the stamp and the review drift apart, both reachable:
(a) The accountant runs "Kontrolli registrid" before the search. MainForm.RunLookupsAsync (MainForm.cs:2486) and PeriodPipeline.RunLookupsAsync (PeriodPipeline.cs:434-437) check only that the period is a draft. With no match run, PersonsOf (LookupRunner.cs:455-459) gives every person the month's last day.
(b) After a run, the accountant moves the row that set the person's day to someone else, or adds or removes lines. The stamp keeps the old day.

Example: the fixture person's Pensionikeskus page says contributions ended on 20.10. Checked for 31.10, they become "not a member" with FactsControlDate 31.10. The salary paid on 05.10 is then built with no II-pillar withholding and no note, because 31.10 is in the month. The same holds for an EMTA residency period that changes mid-month.

A rerun would put it right: LatestLookup is keyed by the exact control date, so the new day has no record and is asked again. But nothing tells the accountant a rerun is due. No decision covers this. The earlier audits closed only the month-level check (audit 2026-11-05 items 63 and 72, decisions 97 and 123), and decision 138 came later and brought in day-level dating.

Major, not critical: the wrong data needs a register change between the two days plus the drift, and a rerun fixes it. But the build gives no sign of the problem.

**Fix:** In PeriodDeclarer, next to FACTS_OF_ANOTHER_MONTH (PeriodDeclarer.cs:482): when fromRegisters is true and FactsControlDate is in the month, work out the person's day as the review stands now, using the same rule as the lookups (LookupRunner.ControlDateOf(period, the person's payout dates as the review hands them out), or LookupRunner.ControlDateFor). If it differs from FactsControlDate, add a note such as FACTS_OF_ANOTHER_DAY: "checked for dd.MM, the review now pays them on dd.MM; run Kontrolli registrid". The same check could also go in ReviewChecks so the grid shows it.

### 6. [minor] A register person's money-in row (credit) counts as a payout day and can move their control date — FIXED (item 56 of the owner's list, 2026-11-11)

bug — `SatellesTSD.Core/Lookups/LookupRunner.cs:168`

The finding holds for credit rows. The employee pass in PeriodMatcher.cs:150/245-266 matches a person's name whatever the row's direction, so a credit row that names the person (for example an advance paid back on 30.10) becomes an in-period hit with that person's PersonKey. LookupRunner.PaidDates (LookupRunner.cs:153-185) checks only hit.InPeriod and the date (line 156). byRun (line 168) then names the register person, and Add(id, date) at line 183 records the credit row's day. The same happens when the accountant's overlay or a part gives the row a person (line 180). ControlDateOf (line 92) takes the latest day. So with salary paid on 05.10 and money in on 30.10, the person is checked for 30.10. This path runs both in ControlDateFor (line 107) and in the run (line 499). Elsewhere money in is never a payout: decision 141 and ReviewWorkspace.cs:711-713 leave it undeclared, ReviewView.cs:160 leaves it out of the sum, and PayeePersons.IsPayeeRow (PayeePersons.cs:42) skips it on the payee path. Decision 138 speaks of the latest "payout", so counting a credit row goes against 138 read together with 141. The effect on tax needs a residency or pension change between the two days, which is rare, and the accountant can see the check day in the grid and log. That keeps it minor.

Part of the finding is dropped. Lines the accountant kept but marked not declared should still count: decision 138 says a row counts unless the accountant gave it to another person or to nobody. DuplicateRow hits need no change either: they are made only in the second pass with PersonKey null (PeriodMatcher.cs:211), so byRun never picks them up.

**Fix:** In PaidDates, skip credit rows at the top of the loop. Change line 156 to `if (!hit.InPeriod || hit.Row.Date is not { } date || hit.Row.Direction == Direction.Credit) continue;`. This covers the register path, the accountant's overlays and the parts alike. Lines added by hand have no direction and stay as they are.

### 7. [minor] Without a match run, hand lines do not set a person's control date: everyone is checked for the month's last day (gap in decision 138) — FIXED (item 56 of the owner's list, 2026-11-11)

gap — `SatellesTSD.Core/Lookups/LookupRunner.cs:101`

Decision 138 (plan line 657) says a line added by hand counts toward a person's control date, and the plan accepts a month paid by hand lines alone with no run (plan line 383). A month can have hand lines and no run. MainForm.AddLine (MainForm.cs:2746-2775) needs only a period. ReviewWorkspace.AddHandLine (ReviewWorkspace.cs:584-588) checks only that the period is a draft. ReviewWorkspace.Load (ReviewWorkspace.cs:89-96) reads the lines even when the run is null. The two places that work out the date, though, return the last day before they read any line. LookupRunner.ControlDateFor (LookupRunner.cs:100-104) returns ControlDateOf(period) when LoadMatchResult is null. LookupRunner.PersonsOf (LookupRunner.cs:454-459) pairs every company person with ControlDateOf(period). The hand-line loop in PaidDates (LookupRunner.cs:136-140) is the only code that reads hand lines, and it runs only when a run exists. Scenario: October has no statement imported (or its run was cleared after files were removed), and the accountant adds a hand line for the fixture person dated 05.10. The card's check and the month's lookup run both ask EMTA and Pensionikeskus about 31.10 instead of 05.10. That gives the wrong answer only when residency or pension status changed between the payout and the month's end, and the accountant can still set the facts by hand. So it is an edge case with a workaround, not wrong data that reaches the file unseen.

**Fix:** Move the hand-line loop out of PaidDates into a helper, e.g. HandLineDates(period), that returns Dictionary<Guid, List<DateOnly>>, and have PaidDates start from it. In ControlDateFor's no-run branch, return ControlDateOf(period, HandLineDates(period).GetValueOrDefault(person.Id) ?? []). In PersonsOf's no-run branch, map each company person to ControlDateOf(period, handDates.GetValueOrDefault(p.Id) ?? []).

### 8. [minor] A paid person outside the register with no personal code gets no line in the lookup run, though a codeless register person gets a SKIPPED line — FIXED (item 56 of the owner's list, 2026-11-11)

gap — `SatellesTSD.Core/Lookups/LookupRunner.cs:501`

This is confirmed in the code. PersonsOf (SatellesTSD.Core/Lookups/LookupRunner.cs:451-507) writes a "SKIPPED: … has no personal code in the register nor on the card; nothing to ask." problem for a register person with no code (lines 479-482). For persons the review pays outside the register (rent payees, rows given by hand, hand lines, all found through PaidDates per decision 138), line 501 keeps only those with `p.PersonalCode is not null`. A paid outside person with no code, such as a non-resident known only by an MRR code or a codeless payee made by PayeePersons, is left out with no problem line, so the run's log never names them. Their declared payments are then refused by ReviewChecks.Of (SatellesTSD.Core/Review/ReviewChecks.cs:78-81) with RESIDENCY_NOT_CHECKED, "not been checked — by the register or by hand". The grid does tell the accountant something is missing, and setting residency by hand on the card is the workaround, so nothing wrong reaches the declaration. The defect is only that the log is silent and treats the two kinds of codeless person differently. Two corrections to the original claim: decision 160's "every person has a line" is about lines of a run that ended before its progress reports were handed over, not about codeless persons, so it does not require this. And the filter is older than the audited range: 12da692 had the same `PersonalCode is not null` filter (old line 370). Commit 56d7c11 rewrote the line under decision 138 and kept the filter. No earlier audit closed it.

**Fix:** In PersonsOf, for each stored person with `paid.ContainsKey(p.Id)` who is not already listed and has no PersonalCode, add `problems.Add($"{Skipped}: {p.FullName} has no personal code; nothing to ask the registers — set the residency on the card.")`. This matches the register path's SKIPPED line.

## The store, the window and the update

### 9. [major] After a store is chosen in the window, an update still restarts on the command line's --store, so the new version opens and upgrades that store instead of the one in hand — FIXED (item 55 of the owner's list, 2026-11-11)

bug — `SatellesTSD/UpdateDialog.cs:258`

The finding is real. Program.StorePathOverride is set once in Program.Main (Program.cs:47) and has a private setter. MainForm._storeOverride is readonly (MainForm.cs:40, 118). Choosing a store in the window does reset the switch's effect: OpenStore(path, chosen: true) sets _oneOff = false and _settings.StorePath = path (MainForm.cs:1319-1325). But UpdateDialog.StartArguments (UpdateDialog.cs:255-261) still passes `--store <original>` to the new version.

The new MainForm then compares that store with settings.StorePath, which is now the chosen store C. They differ, so it treats the original store B as a one-off (MainForm.cs:122), clears LastCompany, and OnLoad opens B (MainForm.cs:1098). Steps: start with `--store B` (either a one-off or the remembered store itself), use Andmebaas > Ava to open C, then install an update. The new version shows B's first company and not C, and keeps C only in the settings.

Decision 147 accepts the restart only "during a one-off" ("nothing is handed on for it"), and it also says a store chosen in the window ends the one-off. So this case is not settled by that decision.

Decision 156's copy tracking is off by the same cause. OfferUpdate snapshots copies of `upgraded = storePath ?? ...`, which is C (MainForm.cs:586-590), while the new version upgrades B. If the update fails, CopyMadeSince/NoteStoreCopy (MainForm.cs:614-617) records nothing for B, so B's before-vN copy is never offered later. The old build reopens C (MainForm.cs:623), which was not touched, so the reopen itself is fine.

No data is lost and no declaration data is wrong. The window title and the store label show B, and opening C again by hand fixes it. Still, the accountant is silently moved to another store's data, so this misleads: major.

**Fix:** Let MainForm decide what is handed on. Pass a `storeToHandOn` into UpdateDialog: `_oneOff ? _services?.StorePath ?? _storeOverride : null`. While a one-off is in hand, hand it on. Once a store has been chosen in the window, hand nothing on, because the settings name the store. StartArguments then uses this value instead of Program.StorePathOverride. Compute `upgraded` from the same rule (`storeToHandOn ?? _settings.StorePath`), so the copies watched belong to the store the new version will open.
