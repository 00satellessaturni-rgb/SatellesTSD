## 1. What the workbook does today (as-is)

One Excel macro workbook, one CONFIG sheet, two buttons on it: **Run main** (formMain) and **Calculator** (formSalCalcV2). Everything below is driven by named blocks on CONFIG (`{employee_define}`, `{payout_define}`, `{category_filters}`, `{category_config}`, `{report_config}`, `{tsdl1_config}`, `{tsdl2_config}`, `{taxes_config}`, `{tsdl1-tor-cat_matrix}`, `{tsdl2-tor-cat_matrix}`, `{system_data}`).

### 1.2 Pass 1 — "Report" (mdlTables.GenerateReport)

Inputs: period (a month; the control date is its last day), company name, `useHttp` flag.

For every TÖR row:
1. Duplicate code/name → row painted yellow, skipped.
2. If `useHttp`: **residency** from the EMTA non-resident register (scrapes `apps.emta.ee/saqu/public/nonresident`, CSRF token + cookie, parses the HTML table of non-residency periods) → "EE" or "mitteresident"; **II pillar** from `pensionikeskus.ee/.../liitumiskontroll/?personCode=` (scrapes the page; finds "liitunud", the start date, "sissemaksed lõppenud", and the rate row valid on the control date) → "II sammas"/"ei ole liitunud"/"kogumispensioni sissemaksed lõppenud" and the rate (2/4/6 % → stored as the text the parser later re-reads).
3. **Name search** in every statement's name column: substring on the last name, then token match (`Like`) for last and first name; if nothing, one character at a time is wild-carded (`*ast`, `L*st`, …) on the last name, then the first name; first-name aliases from `{system_data}` (SERHII,SERGII,SERGEI,…; PAVEL,PAVLO; …). A masked hit must not also match another TÖR person (IsUniqueResult), else it is dropped.
4. Each hit: date must be inside the period month, else noted "kuupaev ei kuulu perioodi". **Category** from the description with per-bank `Like` pattern lists (`{category_filters}`: include list, `;` exclude list); for Trahvid also the payee name. D/C must match the category's side (all are D = outgoing). Two categories matching = error row.
5. Category effects (`{category_config}`): **Palgad** (Palk=Y) adds the absolute amount into the interim report column of that statement; Dividendid, Üür, Kommunaalkulud, Kompensatsioon, Haigusleht, Laenud, TÖR-väline palgad, Trahvid get a sub-table under the main table (Lisatabel=Y) and their own sheet; unmatched → sheet "Tundmatu kategooria". Töötajapõhine marks Palgad/Kompensatsioon/Haigusleht as employee-only; TÖR-väline palgad is explicitly non-employee.
6. After the employee loop, every statement row that no employee matched is categorised on description alone (employee-based categories excluded) and appended to the sub-tables under the payee's raw name.

Output workbook `report-details-<company>-<yyyy-MM-dd_HH-mm-ss>.xlsx` next to the TÖR file: sheet **Vahearuanne** (columns: Töötaja isikukood, Perekonnanimi, Eesnimi, Maksuvaba, [one net-sum column per statement, named `<bank> *1234`], PALK NETO KOKKU (=SUM), Residentsus, Pension, Kontroll-kp, Töötamise alguse aeg, Töötamise liik, Kande olek, Töötamise lõpu aeg; then the sub-tables), **TOR kontroll** (TÖR copy with the found descriptions per statement), **Otsingu kontroll** (every hit), one sheet per category, and a copy of every statement with a "Vaste leitud" column.

**The accountant then edits this file**: fixes names/codes, adds people by hand (with Töötamise liik text), fills **Maksuvaba** (a number = the basic exemption to apply), corrects amounts.

### 1.3 Pass 2 — "TSD" (mdlTables.GenerateTsd)

Input: the edited report (Vahearuanne + TOR kontroll), period, `useHttp`.

Main rows (one per person): TÖR lookup by code, else by names; a person not in TÖR but with a Töötamise liik text is mapped through the matrix name row (partial match) to a TÖR code. Residency/pension are parsed back from the report strings, and fetched if missing and `useHttp`. "lisatulu" = this person's sums in sub-tables whose category carries a TSD code (Üür→57, Haigusleht→24) — it only influences the tax-free decision. Then `cTsdTable.CreateRecord`.

Sub-table rows whose category has a code (Üür, Haigusleht) create their own records with that code; Dividendid, Kommunaalkulud, Kompensatsioon, Laenud, Trahvid create none.

`CreateRecord`: errors if TÖR unresolved / residency unchecked / pension unchecked (residents) / isikukood invalid → yellow row with the text, file name gets "(vead)". Resident → Lisa 1, else Lisa 2. Kande olek 3/4 with net 0 → silently skipped. The matrix column for the TÖR code gives the **TSD code** and seven flags:

| TÖR/cat code | name | Lisa 1 code | TM | TK pers | TK comp | SM | SM min | KP | maksuvaba |
|---|---|---|---|---|---|---|---|---|---|
| 1 | Tööleping | 10 | y | y | y | y | y | y | y |
| 600 | VÕS leping | 17 | y | y | y | y | n | y | y |
| 507 | Viisa – tööleping | 10 | y | y | y | y | y | y | y |
| 602 | Viisa – VÕS | 17 | y | y | y | y | n | y | y |
| uur | Üür | 57 | y | n | n | n | n | n | n |
| haigus | Haigusleht | 24 | y | n | n | n | n | n | n |
| 601 | Juhtimis-/kontrollorgani liige | 21 | y | n | n | y | n | y | y |
| autorent | Autorent | 50 | y | n | n | n | n | n | n |
| 501 | Tasuta töötamine | 10 | y | y | y | y | n | y | y |
| a1t / a1v | A1 tööleping / A1 VÕS | 11 / 19 | n | y | y | y | y/n | y | n |

Lisa 2 (non-residents): 1→120, 600→123, 507→120, 602→123, 501→120, haigus→129, a1t→122, a1v→125, uur→205; no KP, no maksuvaba; SM min only for 1/507/a1t.

`{taxes_config}` (2026 values in the file): TM 0.22; TK 0.016 / 0.008; SM 0.33; SM min base 886/month; KP 0.02 (overridden by the person's own rate when known); maksuvaba 8400/yr (= 700/month, fixed — the 14400/25200/10800 tiers are still in the sheet but the 2026 class skips them); pensioniealine 9312/yr (not used by the TSD path).

`cCalc2026` grosses **net → gross**: gross = (net − TM×maksuvaba) / (1 − KP − TK − TM×(1 − KP − TK)) when net exceeds the exemption, else gross = net/(1 − KP − TK); re-rounds so that gross − KP − TK − TM = net exactly; tax-free capped at net; SM base = gross (+ the increase to the 886 minimum when the flag is on); employer UI; "company expense".

Row written per person (Lisa 1): 1000 code, 1010 name, 1020 payment code, 1030 gross, 1050 A1 country (empty), 1060 SM base, 1070/1080 "0,00", 1090 SM min increase, 1100 SM, 1110 KP, 1120 UI base (= gross), 1130/1140 UI, 1170 TM, 1160_610 exemption used, 640/650 "0,00". Lisa 2: 2000…2170 likewise, 2020 country left EMPTY, 2160 rate.

Outputs: `tsd-details-<company>-<ts>.xlsx` (TSD Lisa 1/2 kontroll + eksport sheets, the report copy) and `tsd-<company>-lisa1.csv` / `-lisa2.csv` (one line per row, values quoted and `;`-separated, sums as "0,00", no header) for the e-MTA Lisa 1 / Lisa 2 import; "tsd(vead)-" when any row has errors.

### 1.4 Calculator (formSalCalcV2)
Gross⇄net for one month with toggles: maksuvaba on/off or a custom amount, SM minimum, employer/employee UI, pension; shows TM, UI, KP, SM, company cost. Dividends are not covered.

Done: people added by hand with a contract type go into TÖR; company name fallback. Open: CSV statement import and SEB headers; a better name-verification algorithm.

### 1.6 Facts to carry over unchanged
- Everything is **per person per month** from NET bank amounts; the gross-up is the firm's own arithmetic, not the bank's.
- Residency and II-pillar facts come from two public web pages, scraped; both parsers are brittle (fixed CSS selectors, cookie names, Estonian phrases).
- Statement layouts are matched by exact header text; several layouts exist only because banks export mojibake or Russian/English headers.
- The accountant's review happens in Excel between the two passes; the report file IS the hand-off.

## 2. What changes in 2026 (andmepõhine TSD / APA TSD)

Sources: the zip `Andmepohine_TSD_2026.zip` (developer guide v1.1 of 30.01.2026, X-tee guide v1.3 of 20.07.2026, business rules v2.0 of 24.07.2026, payment-type matrix of 18.11.2025, taxonomy of 17.10.2025, MTA examples). The two reader notes `apa-xml-reference.md` and `payment-type-mapping.md` (scratchpad, this session) cite file and line for every claim below.

### 2.1 The file
- **One XBRL GL XML instance per company per calendar month** (the month the money was PAID, not the accrual month). Fixed header: one `context` (äriregistrikood + file date), units `eur` and `pure`, `documentInfo` (entriesType=other, uniqueID = regcode-date-time, language=iso639:et, creator, periodCoveredStart/End = the month, sourceApplication, defaultCurrency=iso4217:eur), `entityInformation` (organizationIdentifier + ARIREGISTRIKOOD).
- **Two sections** matter for a private company: `EE0201001` (töötasud: salary 10, VÕS 17, board member 21, employer sick pay 24, severance 33, non-resident 120/123/129/156/138 …) and `EE0201002` (rent 57/50/54/56, non-resident rent 185/205/186, other income 55). An empty section is just `entryHeader` + `entryNumber`. `EE0201003` (erijuhtude SM) is for state bodies and not ours.
- **One `entryDetail` = one payment** (one date, one type, one payee), in strict element order: `lineNumber` (a permanent key, unique per company+month+section across ALL files ever sent), `lineNumberCounter`, `account/accountSub` (TOIMINGUTYYP R/M/T + VALJAMLIIK code + optional country/A1 entries through `segmentParentTuple`), `amount` (**GROSS**), `identifierReference` (`EE`+isikukood, ISIKUKOOD; or the MTA non-resident MRR code), `documentDate` (the payment date, inside the month), `measurable*` (SYNDMUS `TSD01` = calculation date on every payment; `TSD_SMVM` social-tax base; `MVT_610`/`MVT_650`/`MVT_640` exemption used; `TSD_KUUMSUURENDUS` the minimum-SM increase; refunds carry `TSD02` and negative amounts), `taxes*` (`taxAmount`, optional `taxPercentageRate` — required for TSD_KTM on non-residents —, `taxCode` ∈ TSD_SM, TSD_KP, TSD_TK, TSD_TTK, TSD_KTM). `decimals="2"` on every number, dot decimal, dates `yyyy-MM-dd`, UTF-8. **No names are sent.**
- **The submitter supplies gross and the computed taxes.** The rules check each tax against MTA's own figure "within a tolerance" (size unpublished) and refuse taxes that a type cannot carry. No rule found that requires the tax lines to be present or says MTA fills them in (open question for MTA).
- **A1 cases are no longer separate codes** (old 11/19/122/125 die): base code 10/17/21/120/123 + two `accountSub` entries (A1_RIIGID_enum under `RR_A1`, RTK2T2013ap under `RR_TOOKOHA_ASUKOHT`). Non-residents always carry RTK2T2013ap under `RR_MAKSURESIDENTSUSE_RIIK`; tax-treaty rates exist for some types (123 art 14 …) with a residency certificate; EEA residents may get the basic exemption.
- Changes: `M` resends the whole payment under the same `lineNumber`; `T` sends only the key + counter + T and kills the key forever; a confirmed TSD must first be reopened in e-MTA; `entryComment` carries PARANDUSPOHJUS_1..4; previous-year income-tax changes are refused after 15.02.

### 2.2 The round trip
- **Submit**: `POST …/apa-tsd/payments/v1/xtee/submit-data` (multipart, `.xml` or a `.zip` with one XML, ≤ 50 MB, headers `X-Road-Client` + `X-Road-Represented-Party` for a client company) → `{uuid}`; then `GET …/return-data/{uuid}` (204 while processing) → the **feedback report** XML (`processing@result` OK | WARNING | ERROR | PARTLYERROR; per-payment messages tagged WARNING / ERROR_RED / ERROR_BLUE / ERROR_BLACK; the server's own tax figures echoed for clean payments). Black = not saved (resend as R); blue = saved but taxes not counted; red = counted but blocks confirmation; yellow = advisory. Parser traps: decimal commas and dots mixed, a leading space in one error code, a missing counter on black errors, a ZIP when 2+ messages.
- **Confirm** (a separate step): a digitally signed or e-sealed **`.asice`** holding a `confirmDeclaration` XML (regcode, TSD, month, year, which sections have data, the tax totals 110/114–119) → `POST …/confirmations`, poll status; errors DECLARATION_WITH_ERRORS / _DISCREPANCIES / _PROCESSING.
- **Calculator** (`apa-tsd/calculator`, `POST /v1/xtee/tax-calculations`, synchronous): net OR gross in (`netPayment`), one month per file, XBRL GL with taxes out; **excludes A1 cases and dividends**; takes no pension rate/residency input (uses MTA registers). Every documented path is **X-tee only** (security server or a service provider's, with MTA authorisation). Whether a non-X-tee route exists is the subject of the third reader (section 4).

### 2.3 Rates and parameters in the sources (2026)
TM 22 % (10 % for a few types); SM 33 %; SM monthly minimum base 886 (the MTA example uses 820 — ask); TK 1.6 % / TTK 0.8 % (TK dropped for old-age/flexible pensioners); KP = the person's own rate (only 2 % appears in the files); MVT_610 700/month (8400/yr, flat — the 14400/25200 taper is gone), MVT_650 776/month (9312/yr) from 1 January of the year the person reaches pension age; MVT ≤ amount − KP − TK per payment and ≤ the legal monthly total per payer; MVT_640 (III pillar) ≤ 15 % and ≤ 6000/yr. Codes 37/38/167/168 (SM-only pay) exist in the matrix and the calculator list but not in the VALJAMLIIK2023ap dump. Dividends are in neither (they stay on the TSD form's own annex, outside this file).

### 2.4 What stays the same
The TÖR export and the bank statements are still the only inputs the firm has; residency and II-pillar facts still come from the two public web pages (no API found in the files — the third reader checks the web); the accountant still reviews before anything is sent; the gross-up from net is still the firm's own arithmetic (the official calculator cannot do A1 cases and is X-tee-only).

## 3. Gap analysis — workbook vs the 2026 regime

| # | Workbook today | 2026 needs | Consequence for the app |
|---|---|---|---|
| G1 | Output = Lisa 1 / Lisa 2 CSV, one row per person per month | XBRL GL XML, one `entryDetail` per **payment** with its date | New writer; the unit of work changes from person-month to payment. The statement already gives one line per payment, so the natural model is: every matched bank line = one payment line. |
| G2 | Stateless: nothing remembered between months | `lineNumber` is a permanent key per company+month+section; M/T need the original; R on a known key is a hard error | The app needs a **store** (per company: payments sent, their keys, the feedback). Keys must be generated once and never regenerated (e.g. `<regcode>-<yyyyMM>-<section>-<n>` or a GUID, stored). |
| G3 | Exemption 700 applied once per person-month on the summed net | MVT is per payment; the monthly total per payer is checked | An **allocation rule** across a person's payments in the month (first payment takes the exemption up to its cap `amount − KP − TK`, the rest spills to the next). Same for the SM minimum increase (one `TSD_KUUMSUURENDUS`, on one payment, or a zero-amount line). |

## 4. Timeline, channel and design

### 4.1 Timeline (verified on emta.ee 2026-11-03, see `docs/reference/submission-channels.md`)
- APA TSD is **live since 1.10.2026**. October 2026 is the first new-format period, **due 10.11.2026**. September 2026 went the old way (due 12.10.2026).
- The old Lisa 1/2 **XML** import died on 1.10.2026. The old Lisa 1/2 **CSV** upload in e-MTA (what the workbook produces) is a bridge **until 31.12.2027** ("Ajutise üleminekulahendusena … 2027. aasta lõpuni"). Open: whether that CSV must now carry the new codes (MTA question).
- Lisa 3–8 and INF 1 stay form-based until 2027–2028; dividends are outside this file.
- So: **no emergency**. The workbook's CSV keeps the firm legal for 14 months; the app replaces it before 2028.

### 4.2 Channel: three ways in, in this order
1. **e-MTA upload by hand** of the XBRL GL file in the new "väljamaksete vaade" (package I / right "Väljamakseandmete esitamine"). No X-tee, no setup. MTA computes taxes on upload, shows errors in the UI, and the accountant confirms there. This is how the app should ship first.
2. **X-tee REST** (`EE/GOV/70000349` · `apa-tsd` · payments / calculator / declarations): needs an X-tee member + security server (own ≈ €2.5k/yr per RIA, or hosted, or an intermediary), MTA opens the services, each client grants the firm a volitus (XT_MM or "Väljamakseandmete edastamine X-tee kaudu"); the firm sends with `X-Road-Represented-Party`. Fully machine-driven: submit → poll feedback → confirm with a signed/sealed `.asice`. The app's file and parsers are the same; only the transport is added later.
3. Legacy CSV — not built; the workbook covers the bridge.

### 4.3 Shape of the app (recommendation)
- **Three projects**: `SatellesTSD.Core` (models, tax engine, XBRL GL writer/reader, feedback parser, TÖR + statement parsers, matching, category engine — no UI, no database; plain file reads and writes only), `SatellesTSD.Infrastructure` (SQLite store, HTTP lookups, Excel export), `SatellesTSD` (WinForms). `SatellesTSD.Tests` (xUnit) on Core from day one; the official MTA example file is a test fixture the writer must reproduce.
- **Store**: one SQLite file for the firm (all client companies) in a folder the owner picks. Tables: Company, Person (per company: isikukood, names, residency + country + MRR code, II-pillar status/rate + dates, pension-age, A1 + work country, treaty certificate, overrides with "checked on"), StatementLayout (JSON), Category (patterns + code + section + declare), Period (company+month: state draft/exported/uploaded/confirmed), Payment (one per matched bank line: date, payee, net, category, type code, gross + taxes + measurables, `lineNumber`, action R/M/T, feedback colour/messages), Submission (file, time, uuid, result).
- **Pipeline per company-month**: import TÖR + statements → match & categorise → **review grid in the app** (fix names/codes, set type, exemption, "don't declare", add a line by hand) → compute gross + taxes per payment (exemption and SM-minimum allocated across the person's payments in the month) → write XML (+ XSD check) → accountant uploads in e-MTA → outcome recorded (manual, or from the feedback XML when X-tee arrives) → corrections become M/T lines in the next file.
- **Excel stays as an output**: the report-details workbook the accountants know (Vahearuanne, sub-tables, Otsingu kontroll, statement copies) is exported from the same data for checking and filing; import-back is a later slice if the office wants it.
- **Lookups** behind interfaces with cache + manual override: residency (public EMTA form, as today) and II pillar (Pensionikeskus single query, as today); the paid Pensionikeskus XML/mass query and the X-tee SOAP residency service are later options.
- **Tax engine**: a pure class per the 2026 rules (port of `cCalc2026` + MTA's matrix flags per VALJAMLIIK code), net→gross and gross→net, unit-tested against the eight worked figures in MTA's examples and the workbook's formulas; the Calculator form reuses it.
- **UI language**: Estonian, because every term the accountant sees in e-MTA is Estonian (open question 5).

### 4.4 Rejected / deferred
- Building on the legacy CSV (dies 31.12.2027).
- Calling MTA's calculator instead of own arithmetic (X-tee only; no A1; no pension-rate input).
- App-side e-seal signing of the confirmation (needs a signing library + certificate; the accountant confirms in e-MTA).
- Excel as the editing medium between passes (loses the stored keys; two sources of truth).

76. The total line counts the persons of the Vahearuanne — register persons and persons added by hand — and not the rows nobody matched; the search box's filter adds the sum of the rows left shown, so that a filtered grid never passes for the whole.
77. The header row of a bank's sheet may sit anywhere in the first thirty rows; what is above it is not the statement's. A data row never reads as a layout's header, so the deeper look costs nothing.
78. The declaration's cut is the program's setting, not the period's: one choice for every company and month, kept in settings.json. A totals line is known by its person and type (the key "totals:<person>:<type>"; the source text carries the type and the payments' references); it holds no bank row and no hand line's id, so the store's "a bank row feeds one key" rule does not reach it. The taxes of a totals line are computed on the summed net, with the month's exemption and minimum allocated over the types — the figures may differ in cents from the per-payment cut, as the old TSD's did.
79. The two cuts never mix on the server: with lines of one cut sent (or standing beneath an M or R draft), a build in the other is refused rather than cancelling the month wholesale; the other cut's drafts are deleted at the build, never cancelled; a T draft is the accountant's own way out and blocks nothing. The minimum's zero line belongs to both cuts. In the totals cut a refused payment holds its whole type: the type's line stands as it is (a draft of it goes) until the payment is put right or taken out.
80. The end date is shown only for an ended employment: an entry in kande olek 4 (Lõpetatud), or one whose end falls on or before the month's last day. A fixed-term contract still running past the month shows nothing, so the column reads as "this employment has ended". The entry is the employment covering the month, else the latest one begun by the month's end (a contract starting later says nothing of this month).
81. The declaration choice belongs to the person, not to the month: it holds for every month until the card says otherwise, like the minimum's checkbox beside it. "Kaasa" changes the employment's state only — a minimum share of a month the employment ended in is still the days over 30 — and needs the other conditions; "välja" undoes the person's lines rather than leaving them standing, as a payment taken out of the declaration does. (Amended by 137: "kaasa" declares only where the month has a register row or a payment; with neither, the person is shown with INCLUDED_NO_ROW and nothing is built.)
82. The grid shows one direction shape for every bank: the amount without its sign, and "D" or "C" beside it — never the bank's own marker text (Д/К) nor a signed amount. A direction the statement does not state is "D?" (an assumption) or blank (nothing to go on). The card export's amount is the account's: "Amount" in "Payment currency", not the card payment's own currency.

83. The pause dates are no columns of the store: they are read from the cells the store keeps for each register row, by the sheet's kept header row, the same way for a fresh import and for one stored before — so no migration, and every TÖR file already imported shows them. A pause date not understood reads as none, never as a problem: the pause is shown, never declared on. The column follows the entry "Kande olek" shows, so the two never disagree.

84. (Superseded in part by 89.) The minimum share counts the entry standing for the month and, only when its own type carries the minimum, the person's other rows whose type carries it too: a VÕS contract's days do not stretch a Tööleping's minimum, nor a Tööleping's days a board seat's. A paused row counts its days before "Peatamise alguse aeg" and after "Peatamise lõpu aeg", never the pause; a paused row that does not say since when counts nothing. Two valid contracts of different types at once: decision 85, item 11.

85. "By its day" is the payment's own date, the day the money moved — so a final salary of an ended contract paid after a new contract of another type began goes by the new one; the card's switch or the payment's own type corrects it. The card's switch with no type chosen, or with a type the app does not know, changes nothing. The switch is the person's, for every month, like the declaration choice.
86. A copy of a payment row — the same fingerprint and the same bank id (or none on both) as a row of an earlier source of the run, one for one — is listed and never counted or searched; the earlier source holds the original. The fingerprint is decision 23's; the bank id, where the export has one, separates identical same-day payments and tells two exports' copies of one payment apart from two payments alike.
87. An amount counts in euros only: a row in another currency is seen (the grid's Valuuta column) but never summed, declared by default, or accepted when declared — the accountant declares the euro amount on a line added by hand.
88. The program computes a month with its own year's rates and refuses a year it has no rates for, rather than using the latest year's; a new year's rates come with a version.
89. The minimum's share is measured by the rows whose type carries the minimum, whichever row stands for the month (item 13 replaces decision 84's rule that the other rows count only when the standing entry's own type carries the minimum); a paused row — the standing one included — counts its days outside the pause, nothing without a pause start, every day under "kaasa"; a month paused through owes no minimum.
90. A person saved from the card is measured against the copy the card showed: what the accountant left as shown is not written, so the registers' answer written meanwhile stands; "by hand" is a change against the card.
91. Nothing set aside by a restore is ever deleted by the program: a second aside gets a stamped name.
109. A person made for a rent payee becomes an employee the first time a register row lists them: the employment's type, the minimum and the exemption as a new register person gets them, written once and said on the card; the payee binding is kept (amends 108, which only gave the code).
110. The hold of decision 92 lets no draft stand for a held payment: what the server holds stands, what was drafted beside the refused payment goes, and comes back allocated afresh once the payment is put right.
111. A month is stale not only when its files changed after the search but also when it has files to search and no search (amends 98): the lines are never built from no search while a register or a statement is linked.
112. A code they have is never overwritten.

Two persons of the company with the payee's names make nobody the payee and nobody new; the rows nobody matched say so (PAYEE_AMBIGUOUS) until the accountant names the one.

A person made since is not read back into a month declared without them (amends 108).

The accountant's tick or untick on the row ends the word; one hand line pairs with one row.

The period's files are read in the order they were linked (as 86 says), so the first file linked holds the originals.

The Excel report asks before it is written from a stale search (the XML export refuses).

The "not a member" that followed from non-residency goes in the same write as the residency that turns resident: a cancel between the two questions leaves the pension unknown, never the stale inference.

Every month that lists the file must be a Draft; their searches are cleared, and the drafts built from the file's rows go in every Draft month (a month that no longer lists the file may still hold them), counted and said — the months are searched and built again. A line on the server from the file refuses the re-read: the reading stays as its record.

While another Draft month lists the file, it is taken out there first; a month past Draft keeps it as its record for good.

A row the search found for two persons dates nobody until the accountant names one.

The identifier's scheme stays the Äriregister's, the only one the reference names, until MTA says otherwise.

Money that came in is no payout, whatever category the accountant gives the row and whoever they give it to (completes 113): not declared by default, refused when ticked (MONEY_IN), out of the salary sums and of Deklareerimata, and no error of the review's. A salary paid back is a correction of the payment it refunds, made in e-MTA: the program writes no negative line, and the hand-line dialog takes none.
142. A person's code that is no Estonian personal code (the workbook's structure check: eleven digits, the first 1–6, a real birth date; the check digit is still never enforced) refuses every declared payment of the person with CODE_INVALID, a refusal of its own: a residency set by hand does not stand in for a code e-MTA cannot know, and an MRR code beside the code changes nothing, since the declaration names the person by the personal code when one stands (`Person.PayeeId`). The way out is the card: a corrected code, or none and the MRR code instead — the card refuses the code as it is under the same name, and the lookups skip the person until then. The review's own error, not the accountant's choice (Deklareerimata counts it). The declarer decides by the same test (`ReviewChecks.InvalidCode`) before the social-tax-minimum zero line, the one line that never passes the review's checks: CODE_INVALID, nothing built under the code; a draft standing under it (built before the code was found wrong) is withdrawn, since the export takes every draft, and a line on the server stands, nothing cancelled. A codeless store person whom the register now writes with such a code is not given it (`RegisterPersons.Ensure` adopts a register code only when it is a personal code), so a foreign worker named by the MRR code stays so and a code cleared on the card stays cleared; a person first made from such a row keeps the code, bound to it, and the card corrects it in place. Because such a person stays codeless, the fallbacks by names (`RegisterPersons.Find`) hand a store person to one row of the run only (`taken`, kept by the review's load and the lookups alike): a namesake row of the same run, whatever its code, gets a person of its own, the same on every load.
143. The name search goes one step past the workbook: a register name of several words (a two-word surname, a double first name), and every mask of it, is Like that many consecutive tokens of the payee cell, in order (`NameSearch.SpanOf`); a one-word name is Like one token, exactly as before. So the bank's ordinary spaced spelling of such a name is found at the exact level, where the workbook could find only the glued or hyphenated spelling through the mask over the space — which still works. The words out of order or apart are not the name. The glued and the hyphenated spellings ("BenAli", "Ben-Ali") are found as the workbook found them, through the one-word mask over the space, with the uniqueness check (so TAMM MARI LIIS's hit on "Mariliis Tamm" is dropped for TAMM MARILIIS, whose row it is); for a name of several words the one-word masks are tried before the spaced ones (a masked letter), so the joining is tried before a fuzzier spelling. A span of several words found with no first name beside it is another person's row and does not end the search, as a one-word surname found alone did and does (the workbook's rule at its own levels): "Kati Ben Ali" leaves "Mari BenAli" to be found through the mask. The first level that hits takes every row at it, as ever: the spaced spelling found at the exact level leaves a glued row of the same source for the hand. A first name of several words must stand together on one side of the surname, as it stands in the cell. A mask one word of which is "*" alone (a one-letter word masked) means nothing. The uniqueness check reads the masks as before, and a mask of several words also means a person whose name is one of its words, whole ("Mari Sen Ali" found for BEN ALI through "*EN ALI" could be ALI MARI's row: dropped, hers by her exact names; a surname merely holding a word of the mask is no competitor). A row two persons find by their exact names where every word of the one name is among the other's (ALI MARI within BEN ALI MARI) is the longer name's alone, said as NAME_CONTAINED — the workbook, which never found the longer name, gave it to the shorter; names of a length (namesakes), and a cell naming two people ("Mari Ben Ali ja Jaan Tamm"), stay shared. The reproduction of the workbook's reports (decision 27's test) counts the rows found through a mask holding a space apart: few, in one company, their amounts added to the expected sums. Nothing is said on the person: the rows are found.
144. The country is the accountant's entry alone — the register does not give it, the EMTA page says resident or not — and stays optional (the line without it is declared and noted, NO_RESIDENCE_COUNTRY): an empty country refuses nothing, since MTA judges the exemption by its own register (KR_MVT_06) and the certificate (KR_MVT_07), which the program cannot see. The way out is the card: the tick off, or the country corrected.
145. What the accountant typed on the person card is never lost to an error box or for want of a way back: the question asked before an action that needs the card settled is Yes / No / Cancel (`MainForm.ResolveDirtyPanel` → Saved, Dropped, Kept). Kept — Cancel, or Yes with a save that could not happen — leaves the card as typed and stops the action that asked (`SettleCard`): another person picked (the selection goes back, after the grid's own event), the window's or the company's closing, another store opened, the import, the search, the lookups, the build, the export, the report, the feedback read, the update, and another company, year or month picked (settled before anything is loaded or remembered; the pickers go back). A search that hid the person being edited is cleared on the way back, so the grid, the payments and the card are one person's. The persons grid shows a person on its current row's change as well as on the selection's, since a row made current in code raises the selection's event while the old row is still current.
146. A batch of files is the single-file change done file by file under one question: each file in its own transaction, the run's second word asked once and the run cleared only in the transaction of a file it took; a file refused (another month keeps it, a line on the server) is told at the end and the others still go; declining the run's word stops there, the run and the files not yet done left as they were. The unlisted among the chosen are passed over by "Eemalda perioodist". "Loe uuesti" stays one file at a time, each file's carry-over its own to read.
147. `--store` is a one-off, as the README always said: while the open store is the command line's and not the remembered one, `MainForm.SaveSettings` writes the settings with the store, the company and the month as they were at the start (`AppSettings.SavedWith`), whatever the session shows; the memory in use still follows the session, since the pickers are filled from it. An update during a one-off restarts on the one-off store's first company and the remembered month: the one-off is passing, nothing is handed on for it. A store chosen in the window's dialog ends the one-off: it is remembered, with the company and the month shown in it.
148. A conflict of categories is the run's finding, not the row's state: `ReviewPayment.ConflictingCategories` holds the categories the categorizer matched for an Ambiguous verdict (in the catalog's order), empty for every other verdict and for a line added by hand, and the tab "Kategooriate konflikt" lists the rows that carry any, whether the accountant has since picked a category or not (the category column shows the pick), so the tab is where those picks are checked; a re-run over a changed catalog finds them anew. A category found on the wrong side of D/C ("viga: [X] D/C kontroll") is no conflict of two categories and is not listed. The tab stands whenever a company is shown, empty or not, like "Tundmatu kategooria".
149. Another store is opened first and the store in hand is let go of only once it stands (`MainForm.OpenStore`): a failed open says why and leaves the window as it was, where it used to leave it with no store for the rest of the session. The store in hand is shown afresh after the failure, since the card's unsaved edits were settled (saved or dropped) before the open was tried. The same file again (one file under two spellings included, `FileIdentity.Same`) is closed first and then opened, as before, since one file is not opened twice; so is the update's own reopening and the start, which have no store in hand.
151. A refused version takes the verdict of a report that shows it saved (`SqliteStore.RecordFeedback`): the version is of the submission the report is read onto, it is Rejected, its key has no later version but refused ones, and the report's severity for the line is none, a warning, blue or red: Accepted or NeedsChange, Cancelled or Review for a T, as a pending version would get. It is e-MTA's word about this very file, whatever refused the version before (the file as a whole, most often). A black line stays Rejected; a later version of the key that stands (a draft, a sent or a settled one) speaks for the key and the old one is left as it is, while a later version that is itself Rejected speaks for nothing.
152. A submission keeps the path its file was written to, in the column that held the name: the name is what is shown (`Submission.FileName`), the path what a withdrawal uses (`Submission.FilePath`, null for an export made before this: the export folder last used is looked in then). No schema step. `PeriodSubmitter.Withdraw` sets the file aside after the store's part is done (`WithdrawnFile`: SetAside with the new name, NotFound, Unreachable when the folder itself cannot be reached and the file may still be there, FolderUnknown, Failed with the reason) by renaming it with `.tagasi-voetud` (a number after it when that name is taken): out of the upload's way, never deleted, never a reason to refuse the withdrawal. When the stored path leads nowhere from this computer (the share under another drive letter, a store moved), the file of that name in the export folder last used is the same export and is set aside there. An older version of the program opening such a store shows the whole path where it showed the name: nothing in it depends on the text.
130. The store's upgrade is one transaction: a failure leaves the file at the version it was, so the copy set aside before an upgrade (68) is always a true pre-upgrade store. A revert of an update that fails half-way leaves the new program whole, its exe and schemas back from the failed folder, and says so.
92. A refused payment's line that stands on the server and used the month's exemption or carries the minimum holds the person's other payments of the month: none is allocated or rebuilt until the payment is put right or taken out of the declaration, rather than giving them the pool again or computing around a figure the server may not hold. What stands, stands; nothing is cancelled.
93. A black `KR_XBRL_VALJAMAKSED_5` is MTA's proof that the key is not on the server: the key's earlier Accepted and NeedsChange versions become Rejected with the pending ones (amends decision 12's "never downgrades what MTA already saved" — an Accepted that MTA itself says it does not hold was never saved). If the proof was misapplied, the R it leads to comes back black `_4`, which puts the key under review again.
94. "Märgi kinnitatuks" asks for the force while a line was refused by MTA (amends decision 51): a refused line is not on the server, so the month confirmed without it is not the month the review shows.
95. A store person bound to a register key is never bound to another: when a later month's register writes the person otherwise (with the code added), the person is found by code or by the names, the code is written onto a codeless person, and the first binding stands; a coded row beside the codeless row of the same names in one search is a namesake, another person. The reverse — a coded person a later register writes without the code — is found by names only among codeless persons and stays a separate person, said in the review as now.
96. The export's check is a build run and undone: what "Koosta read" would make now against the drafts that stand, by key, action, source, person, net and the line itself (its counter aside). A difference asks; a stale search refuses the export; a build the month refuses otherwise (another cut on the server, no rates, a stale search) cannot be told and is only said.
97. The registers are asked only for a month in Draft. The person keeps the day the facts were asked for; a build of another month says so when the residency or the pension came from the registers (a note, never a refusal — the facts are the person's, not the month's, decision 64).
98. A search is stale when the files linked to the month are not those it read — a register sheet, or a statement sheet with a layout, linked or unlinked since — compared by sheet, never by time; the lines are built only from a search that saw every file.
99. "Töötamise alguse aeg" and "Peatamise lõpu aeg" follow the entry "Kande olek" shows (decision 83), never another row of the person: the five columns of the contract read as one employment. The end date keeps its own rule (decision 80).
100. Income for the "Deklareerimata" sum is what the review would declare by its category or type: a payment of the month (not a copy, decision 86) of a salary or coded category or given a type, and any payment ticked and refused; a codeless category's payment is found, never declared, and is not counted (decision 40), nor one of another month unless ticked. Under the totals cut, a ticked payment of a type a refused payment holds is listed as held (decision 79). A row in another currency is listed, never summed, and is no error: it is declared in euros by hand (decision 87). On the rows nobody matched only a ticked payment counts. The colour is for what nobody chose; a choice is still summed, so the grid never hides income.
101. A grid's cursor is reset on the way out of every work the window waits on, not only the lookups: import, search and build hold the wait cursor the same way. The progress is the lookups': the other runs are short.
102. The country of tax residence is expected, not required: without it the line is still built and sent, and the build says so; a non-resident's line refused by MTA for it (KR_ISIK_6) is put right with an M once the country is on the card. TÖR's "Riigi kood" is never taken for the residence country.
103. A non-resident added by hand is checked by hand on the day added (EMTA cannot be asked for a person without an Estonian code); a resident added by hand is asked of EMTA as before.
104. The declaration's totals are what the company owes MTA for the month as the lines stand: the standing version of every key — a draft, a line sent, on the server or under review — and never a refused attempt (not on the server), a cancelled key, nor a T (it takes a line back). The taxes are TM, SM (the minimum's increase within it), TK, TTK and KP: the employer's own and those it withholds, all paid to MTA. A refund line's negative figures lower them. The figures are the app's, not MTA's: the feedback's own taxes stay in the feedback tooltip.
105. The window's layout is kept in settings.json: the normal size and place (the size before maximizing for a maximized window), the maximized state (a window closed minimized comes back as it was before), the card's width and the persons grid's height; column widths are not kept (they size to their content). The saved place is taken when a screen shows 120 × 20 px of its title bar, else the window opens centred with its size; a window flush against a screen's edge (snapped) comes back as it was, its invisible border allowed for. The persons grid and the card are fixed panels: a wrapped toolbar, the log or a resized window take from the payments grid and the tabs, and a fixed panel shrinks only when the window gets too small for it (each panel keeps at least 160 px, the grids 80).
106. The Vaade menu's salary-only choice hides the persons grid's columns per source (each statement's and "käsitsi"); every other column stays, "Deklareerimata" too. It is a check item, kept in settings.json, applied when the grid is filled and at once when clicked; a current cell in a hidden column moves to PALK NETO KOKKU on the same row, so the person stays selected.
107. "*proovip?ev*" is the owner's addition to the workbook's patterns: in the standard filter set (every bank's), for Palgad (the register's employees) and TÖR-väline palgad (anybody else), so a trial day is salary in either pass. A month's stored run keeps the catalog it was made with: the pattern counts there once the month is matched again. The tests that hold the catalog to the workbook's CONFIG sheet and its reports use the default less the owner's additions.
108. A row nobody of the register was found for, in the month, whose category (the run's, or the accountant's) is declared on its own code and is not one for employees only — today Üür (57 / 205) — has its payee as its default person, when the payee is a natural person: two words or more, no digits, no legal form (OÜ or O.Ü., AS, MTÜ, KÜ, osaühing, korteriühistu, linnavalitsus, SIA, UAB, ООО …). The person is found among the company's persons — bound to the payee's name, else by the personal code the statement gives, else the one person whose names are the payee's words in any order — else created: named from the statement (the last word the last name, capitals written as a name), the statement's personal code when it is one, no basic exemption, no social-tax minimum, bound by the key "payee:<the words>" so a name or code corrected on the card keeps the link. Two persons of the same names make nobody the default, and nobody new. Persons are made only while the month is a Draft; a month past it, and a row the accountant gave a person or nobody, find the payee already made but make none. The payee then shows as a person in the persons grid, the payment declared by default; the month's lookups ask for a payee with a personal code on the day of the rent (and so for any person outside the register the accountant gave a row or a hand line of the month; a row given nobody asks nobody), and one without a code is refused by the checks until the card has one. A register that later lists a codeless payee of the same names finds that person (and gives the code).
