# SatellesTSD — second audit, after the recent improvements (2026-11-09, version 0.23.0, commit f71c79a)

**How it was made.** Six Opus finders over the work since the criticals (the diff from 62f9fa8 to f71c79a: plan items 14–18, decisions 92–108): four on the changed areas (matching and review; the declaring; the lookups, the store and the window; the Excel report and the stored data), one regression sweep of the whole monthly flow on the current code, and one for overlooked items (the owner's words in items 13–18 against the code and the tests, the first audit's open items that the recent work made worse, the README and the plan). An Opus refuter tried to disprove every finding; what survived is listed below with the refuter's corrected claim and severity. 47 findings were raised, 11 refuted, 36 confirmed: 3 critical, 6 major, 23 minor, 4 nits. Several issues were found from two or three lenses and appear more than once; the short list names the distinct ones. The three criticals of the short list were fixed the same day on the owner's word, item 20 of the plan's owner's list; the rest await the owner's choice. The first audit's open items (its short list 8–18 were fixed in item 14) are not repeated here unless the recent work made them worse.

Severity: critical = wrong tax or declaration data, or data loss; major = a flow the accountant needs that breaks or misleads; minor = a wrong message or an edge case with a workaround; nit = cosmetic.

## The short list — distinct issues that matter

**Wrong declared figures or lost lines (critical)**

1. **A rent payee made a person (decision 108) who later joins the register keeps "no exemption, no minimum".** — fixed (owner's list item 20) PayeePersons creates the payee with both off; when a later TÖR lists the same person, RegisterPersons finds the payee and only adds the code, never the register's defaults. The employee's salary is then declared without the social-tax minimum top-up and without the basic exemption, with no message; only "ei" in Maksuvaba and the card show it (items 1, 17, 24).
2. **The hold of decision 92 keeps drafts that were allocated against a draft the same build deletes, and the export sends them.** — fixed (owner's list item 20) While a refused payment's line on the server holds the person, the other payments' existing drafts are reported Kept; they were allocated together with the refused payment's draft, which the build just deleted. The export's check reproduces the hold and asks nothing, so the month's exemption or minimum can go out twice; held drafts that no longer match the review go out unasked (items 6 and 19).
3. **Unlinking a file the run took clears the run, and "Koosta read" then builds from no search at all.** — fixed (owner's list item 20) The store refuses to unlink a file the run used, so the Failid dialog clears the run first; with no stored run the stale flag is false, so the build proceeds, claims nothing, deletes every bank-row draft and drafts a T for every bank-row line on the server; the export check confirms it (item 16).

**A flow that breaks or misleads (major)**

4. The accountant's decisions stay on a row that a later-linked file turns into the copy (decision 86); the original row has no overlay and stays nobody's, so the payment drops out of the declaration without a warning. The sources' order is by import time, not link time, against the plan's wording (item 18).
5. A credit (money-in) row given Üür by hand makes the payer a person and declares the money as rent paid: a new automatic path into the first audit's open item 20 (item 25).
6. Months reviewed before 0.23.0: a nobody's rent row now defaults to a payee person found by names, in a Draft at the upgrade or after Reopen — so a rent already declared on a hand line for that person is declared twice; and in a month past Draft the review and the report show the row as declared although no line exists for it (items 2, 20, 32, 33).
7. A black KR_XBRL_VALJAMAKSED_5 read from a version that is no longer pending rejects a later pending version of the key (a re-read report); it repairs itself through the next round, but the window shows the version refused with its own green report (items 7 and 19 of the window area).
8. "Märgi kinnitatuks" with both an open line and a refused one throws only the open-lines message; the single force question then confirms the month without naming the refused lines, so decision 94's question is never put (item 8).

**Minor, but worth a word from the owner:** a payee with two namesakes is left undeclared without a sign (3); joint-account names and address-pattern false positives become declared rent persons (4); a payee bound by names never takes the personal code a later statement gives (5, 34); MarkConfirmed counts refused keys no build will resend (12); payments held by decision 92 are missing from Deklareerimata (13, 26); the export's check builds in the Seaded cut, so a cut switch is reported as "the review changed" (14, 28); the feedback tooltip shows TSD_KTM with no figure of ours beside it (16); one control date for two facts hides a failed pension lookup (18); the persons search still matches the hidden source columns in the salary-only view (20, 41); the Deklaratsioon sheet has no totals and does not follow decision 104 (27, 45); the report is built from a stale search without a word (46); the Vahearuanne lacks the grid's newer columns (35, 47); "proovipäeva raha" is an ambiguous verdict between Palgad and Kompensatsioon (33); the README leaves out the Vaade menu, the saved layout and the current settings (36).

**Suggested order.** 1, 2 and 3 first, together: 1 and 3 are small (the register defaults when a payee-bound person is first met from a register row; "linked sheets, no run" counted as stale), 2 is a rule change in the hold (delete the held drafts, leave only the server's lines standing, and let the export check report a held person). Then 6 and 4, which need a decision on the upgrade path and on moving an overlay to the original; 5 is one line; 7 and 8 are small.

### 5. [minor] The statement's personal code is never written onto a payee person created without one

### 7. [minor] A black _5 read from a non-pending version rejects a later pending version of the key

**Fix:** Restrict the loop to earlier versions (v.Version < payment.Version) for the pending case too, or run the branch only when the reported version was itself pending.
